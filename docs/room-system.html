The room — how it works

tackle · one project · two machines · five units · one rule: the model acts, the ledger decides

The room is not an agent and not a transcript. It is a small deterministic ledger that answers three questions — what is the work, who may touch it, and what happened — and a set of taps that answer them from facts. No model runs in the control plane. That is what makes it testable, cheap, and boring in the right way.

1 · Who writes what

Four writers, four kinds of truth. GitHub owns code and review threads. Linear owns issue state, and its GitHub integration is the writer — the room only watches. Each host owns its repo, its CLI, and its model keys. The room owns the one thing none of them owns: who is on what.

The room's only credential is a Slack bot scoped to one channel. It holds no repository token, no model key, and no write token for Linear. Every effect on the world leaves from a host, because a host is the only thing that can prove it has the repository.

2 · The five units

Identity is derived, never entered by hand. A chit is ticket @ pr : path:line for a review thread, or ticket @ build before a thread exists. The layer is the topological rank of the PR in its base chain, which is why “reviewable” can be computed instead of announced. A sweep is the set of unanswered chits at one layer; a train is the layers, in order.

Why the thread and not the ticket: in the multi-season work, 59 blocker threads were opened and 59 were answered, median 43 h later, each at a path and a line. Almost every session started from one of those permalinks. The ticket id appeared in 5 of 40 sessions. The address people actually use is the thread.

3 · The life of a chit

The happy path is nine states and every one is observable from outside: a claim from the room, a commit from GitHub, a review from GitHub, a deploy from the pipeline. The exceptions are the reason the ledger exists. A lease can expire while the process is only paused — so the claim carries an epoch and a stale write is refused. Linear can close a ticket while an agent is still editing — so closed.external interrupts the turn. A PR can be superseded by a lower one in the stack — so abandoned is a state, not a deletion.

4 · One day, two humans

Nothing here is a notification per event. The room computes that a layer is reviewable, sends one digest to Slack and one card to the other human, and when the blockers arrive it mints them as a set. The owner gets the set, fixes it in a single turn, replies per thread, and the next sweep is scheduled. The merge is a single human approval for an ordered train, executed by the host that holds the claim.

If host A is asleep at step 8, the room offers the changeset to host B with a new epoch. If host A wakes and tries to push, it gets a 409 and reloads. That is the whole multiplayer story: not shared context, a fenced claim.

5 · Out by facts, in by address

Outbound runs on effects, not narration: 44,433 of 44,498 tool calls in the Shakti logs were fabric_exec, so a hook that watches individual tools sees almost nothing. The tap reads what the program changed — paths, commands, commits, the PR — and writes an idempotent fact to a local outbox. The outbox is the offline story: the session never waits for the room.

Inbound has three channels and only two cost tokens. A card is a transcript entry that is rendered but never sent to the model. An addressed message becomes a turn. A pull is you asking. Everything else waits in the room.

6 · The invariants

# Invariant Checked by
1 No effect without an older intent. outbox pair, replayed
2 No claim without a live epoch; stale writes are refused, never merged. fencing test, 100 kills
3 A chit has exactly one owner at a time, or none. property test over the state graph
4 The room never writes Linear state. no write token exists
5 The room holds no repo or model credentials. secret list is one Slack bot
6 Merge is not done; deployed is not closed. state graph, no shortcut edge
7 A fact is derived, never narrated. the tap has no model
8 A card costs zero tokens; a turn is addressed. Pi API: appendEntry vs sendMessage

7 · What runs where

Piece Runs Holds May write
board nowhere — a format chit, claim, layer, sweep, receipt, presence nothing
room SQLite first, Durable Object later the ledger; read caches of GH and Linear its own state · Slack
tap each laptop, as a Pi extension outbox, claim cache, pre-exec fence GitHub via the host's CLI
drift CI or a laptop ticket anchors → code anchors nothing

Build order

  1. board — the six records and the invariants, as a zero-dependency format with property tests.
  2. tap on one host, room on SQLite: capture one real week of threads. No DO.
  3. sweep + changeset routing, with Slack as a single digest. Prove the 43 h becomes minutes.
  4. train execution and Linear observation, including closed.external and parent rollup.
  5. DO adapter and the second host; then drift as a jig engine over the ticket anchors.

The order is the argument: the ledger and the interrupt are proved on one laptop before the distributed runtime is bought. A room that cannot survive kill -9 locally will not survive an eviction.
