The room — project sessions that outlive a laptop

tackle · one Linear project · one GitHub label · two humans, two Pi sessions · Oct 2026

A room is not a longer conversation. It is a small authoritative record of who is on what, sitting beside two conversations that stay one-to-one. The transcript stays on the laptop; the room holds claims, receipts and presence. Everything below follows from three corrections to the original sketch: the room must never own Linear's state, the room must never be in the path of a push, and the model must never be asked to broadcast.

1 · Who writes what

Linear and GitHub already talk to each other. With Linear's GitHub integration configured to move an issue to Done when its pull request merges, the issue transition is a third party's write. Any room that also writes that state is now racing an integration it cannot see, and the loser is whichever webhook arrives second.

The rule: the room writes claims and receipts. It reads code state from GitHub and issue state from Linear. It never writes issue state.

That leaves one join key, and it is already the one Linear's integration uses: the human identifier, AUT-118. The branch is aut-118/<slug>; the PR title starts with AUT-118 . The link exists before the PR does, so both systems derive it themselves and nobody stores it as a foreign key.

Fact Authoritative writer The room's job
code, branch, PR GitHub mirror, and gate the claim before a push
issue state Linear — via its GitHub integration observe, and treat a close as an interrupt
who is on what the room sole writer; lease with a fencing epoch
what was tried each laptop a pointer, never a copy
review decision a human, in GitHub or Slack record the receipt

2 · The interrupt you have to model

The close can beat the merge. A hotfix PR titles itself with the same identifier, or a human closes the ticket while an agent is still editing. Linear fires issue.closed; the agent's own PR has not merged. A room that only reconciles on merge will keep an agent working on a dead chit, open a second PR, and then discover the ticket was closed twenty minutes ago.

Two consequences. The chit has a terminal state that the room did not cause: closed.external, distinct from merged. And the host needs an inbound interrupt that can abort a turn mid-flight — which is exactly what a durable harness gives you and a chat loop does not.

3 · Three channels into a one-to-one session

The pair-programming feel survives only if the room is a sideband. So the room gets three ways in, and only two of them cross into the model's context. Pi 1.3.0 already distinguishes them: appendEntry writes a transcript entry that is rendered but not sent to the model, while sendMessage with deliverAs becomes a turn. A third path is a deliberate pull.

What earns a wake

Event Surface Context cost
another host claims or releases any chit room card 0
someone edits a path you hold room card 0
your PR becomes reviewable card + Slack digest 0
a review lands on your PR next turn, summarised one turn
a chit you own is closed externally interrupt + turn one turn, aborts work
someone @-mentions you in the room next turn one turn
anything else room log 0, until pulled

4 · Broadcast without trusting the model

The model does not decide what the room hears. The harness does. Pi's extension API exposes the events; a hook derives a fact, writes it to a local outbox, and a drainer sends it. If the network or the object is down, the outbox is the queue and the turn is unaffected.

Pi event Fact derived Why it is trustworthy
tool_call (pre) a fence decision it can refuse the call; enforcement, not etiquette
tool_execution_end paths read/written, command run, error it happened, whatever the model says
turn_end outcome + one-line intent turn boundary, idempotent key
user_bash what you ran the human's actions belong in the record too
message_end a truncated summary line commentary, never the transcript
session_start / _shutdown presence, heartbeat the one thing that expires

Each fact is keyed by (sessionId, turnIndex, toolCallId), so a retry is a no-op. The room stores facts, not prose: a chit, a host, a kind, a set of paths, an intent line. That is small enough to send over a socket and cheap enough to keep for a year.

5 · Two hosts, one chit

A lease is not a lock on a file; it is the right to act. It carries an epoch, every write carries the epoch, and the room refuses writes from a stale one. This is the only thing that survives the worst failure: a process that is paused, not dead, and therefore never learns it lost.

Three layers, in order of hardness. The claim is the lease. The path claim is a glob the room knows about, enforced by the tool_call pre-hook (refuse an edit to a path another live host holds). The branch is per chit, so a second push to aut-118/... fails in git, which is another free mutex. The ergonomic layer — “Ed is in packages/foo” — is a card, not a safety mechanism.

What is missing is small and specific: a board schema — chit, claim, receipt, presence — plus the routing policy that decides which human's mailbox gets a chit. That is four record types and one rule, on top of a mailbox that already has leases, receipts and an attention model.

And tools/foreman is the wrong base. It is a batch harness: one driver, one repo, a task chain, spend until the budget yields. It has no peers, no inbox, no receipts, and no human. Keep two things from it — the budget gate and the requestId discipline — and let the rest go.

7 · Slack, without the noise

Slack is the human-to-human channel, and the room only borrows it for one thing: the review request. One thread per reviewable unit, opened when the unit becomes reviewable, edited as it changes — never a message per event.

The bot posts five lines: what changed, why, what is risky, where to look, what decision is needed. Replies in the thread are ingested as decisions addressed to the chit, and only a decision or a direct question wakes an owner. Everything else is a card. The ceiling is a rate, not a hope: at most one new thread per reviewable, at most a handful a day, and a digest interval instead of a stream — the same discipline ccDigestMinutes already encodes.

8 · Build order

# Move Done when
0 Instrument the current flow for one week: raw webhooks, gh events, session JSONL a replayable trace to diff against
1 Room as a sideband with no Cloudflare: local SQLite, one project, two hosts, pi-ratking-style cards kill either host 100× → zero duplicate PRs, one live claimant, no lost chit
2 GitHub/Linear projection + closed.external interrupt close before merge aborts the turn; no reopen; the ledger explains why
3 Durable Object + Slack review digest delete the object, rebuild from webhooks and both APIs, same board; Slack stays under the thread ceiling
4 Swap in rat-king's mailbox when its crypto review lands a third host joins from the format doc alone

The order is the argument: prove the record and the interrupt on one machine before buying a distributed runtime. A room that cannot survive kill -9 on a laptop will not survive Cloudflare.
